# ⚠️ Data Loading Issues

Two issues were identified during ingestion into SQL Server. Both were investigated and remediated before downstream analytics and machine learning workflows were performed.

---

## Issue 1: Missing Patient Record After BULK INSERT

### 🔎 What Happened?

After executing `BULK INSERT` on `patients.csv`, only **973 of the expected 974 patient records** were loaded.

A foreign-key integrity check using a `LEFT JOIN` between encounters and patients revealed **19 orphan encounters** associated with the missing patient:

```text
Patient ID:
204f8028-72f8-d6f8-761f-79ebf9f02311
```

This patient record corresponded to:

```text
Mrs. Melaine933 Hintz995
```

### 🧪 Root Cause

The most likely cause was the presence of **special characters within quoted CSV fields** that SQL Server 2019 misparsed during `BULK INSERT`, despite using:

```sql
FORMAT = 'CSV'
```

### 🛠️ Resolution

The `patients.csv` file was loaded using the **SSMS Import Flat File Wizard**, which provided more robust handling of quoted fields.

The data was initially imported into a staging table and then transformed before being merged into the main patient table. This process included:

- Converting empty strings to `NULL`
- Safely converting date fields
- Preserving the missing patient record
- Restoring referential integrity with encounter data

Example transformation pattern:

```sql
NULLIF(column_name, '')
```

```sql
TRY_CAST(NULLIF(column_name, '') AS DATE)
```

### 📈 Analytical Impact

Without remediation:

- **19 encounters** would remain disconnected from patient demographics.
- These encounters represented approximately **0.07% of the total encounter data**.
- Encounter-level analysis could continue, but demographic and patient-level joins would be incomplete.

> [!IMPORTANT]
> Although the numerical impact was small, the issue was fixed to preserve **referential integrity** and ensure the analytical dataset was complete.

**Final status:** ✅ Resolved — **974 / 974 patients successfully loaded**

## Issue 2: Empty Strings Loaded Instead of NULL Values

### 🔎 What Happened?

Initial validation queries showed **zero `NULL` values** in optional patient attributes such as:

- `DEATHDATE`
- `ZIP`
- `MARITAL`
- `SUFFIX`

This was immediately suspicious.

For example, the source data contained:

- **154 patients with a populated death date**
- **142 patients without a ZIP code**

However, the initial load failed to represent missing values correctly.

Inspection revealed that blank CSV fields had been imported as:

```text
''
```

rather than database `NULL` values.

### ⚠️ Why This Was Critical

This created a potentially serious semantic error.

For example, mortality-related analysis could incorrectly treat blank strings as populated values or fail to distinguish missing values correctly.

Without proper normalization:

- Patient mortality analysis would be unreliable.
- Missing demographic values would not be correctly identified.
- Data validation checks could produce misleading results.
- The **"encounters after death"** check could falsely report zero records.

### 🛠️ Resolution

#### Patients

The patient data was reloaded and normalized using explicit conversion logic:

```sql
NULLIF(column_name, '')
```

Date fields were safely parsed using:

```sql
TRY_CAST(NULLIF(column_name, '') AS DATE)
```

#### Encounters and Procedures

Optional text fields containing empty strings were normalized using `UPDATE` statements.

Affected fields included:

```text
REASONCODE
REASONDESCRIPTION
```

Empty strings were converted to proper SQL `NULL` values.

### 📈 Analytical Impact

> [!WARNING]
> If left unresolved, missing-value logic across the entire analytics pipeline would have been unreliable.

The most significant risk was incorrect mortality analysis, where downstream logic could incorrectly conclude that **all patients were alive or that mortality fields contained no missing values**.

**Final status:** ✅ Resolved — missing values normalized to proper SQL `NULL`s

# 📝 Documented Findings Not Treated as Errors

The following findings were investigated but **not corrected or removed**.

They are considered either legitimate characteristics of the dataset or cases requiring context-specific interpretation.

Documenting them explicitly prevents downstream users from accidentally treating them as data defects.

---

## Finding A: Missing Encounter Reason Codes

### Observation

Approximately **70% of encounter `REASONCODE` values are `NULL`**.

### Interpretation

Many encounters represent:

- Routine wellness visits
- Preventive screenings
- General ambulatory care
- Other visits without a specific diagnosis recorded as the encounter reason

This pattern is consistent with healthcare documentation, where not every patient interaction is associated with a specific diagnosis code.

### Decision

**Retain `NULL` values.**

Analyses involving encounter reasons should explicitly decide whether missing reasons should be:

- Included as an **"Unknown / Not Recorded"** category, or
- Excluded from diagnosis-specific analysis

> [!NOTE]
> Missing reason codes should not automatically be interpreted as missing or invalid encounter records.

---

## Finding B: Encounters Recorded After the Patient's Death Date

### Observation

**53 encounters** occurred after the corresponding patient's recorded death date.

### Interpretation

These records may represent administrative or financial activity associated with a patient after death, such as:

- Final billing reconciliation
- Certificate or administrative processing
- Claims processing
- Other posthumous administrative transactions

### Decision

The records are retained, with analysis-specific handling:

| Analytical Context | Treatment |
|---|---|
| Financial analysis | ✅ Include |
| Cost analysis | ✅ Include |
| Healthcare utilisation | Context-dependent |
| Patient behaviour analysis | ❌ Exclude |
| Patient activity metrics | ❌ Exclude |

> [!IMPORTANT]
> An encounter timestamp after death does not necessarily imply that the patient physically received care after death. The record may reflect **administrative activity rather than patient behaviour**.

## Finding C: High-Frequency Chronic-Care Patient

### Observation

One patient has an unusually high number of lifetime encounters:

```text
Patient ID:
1712d26d-822d-1e3a-2267-0a9dba31d7c8
```

```text
Patient:
Kimberly627 Collier206
```

| Metric | Value |
|---|---:|
| Lifetime encounters | **1,381** |
| Encounter class | Predominantly ambulatory |
| Next-highest patient | 877 encounters |

### Interpretation

This pattern is consistent with a **high-frequency chronic-care profile**.

A patient receiving recurring long-term treatment—for example, dialysis or another chronic-care service—can generate a large number of routine ambulatory encounters.

Therefore, the record was **not treated as an outlier to be removed**.

### Decision

The patient remains in the dataset.

However, readmission and utilisation visualisations should account for the concentration effect.

Recommended approaches include:

- Explicitly flagging the patient as a high-frequency utilisation case.
- Separating ambulatory encounters from inpatient encounters.
- Filtering the patient in selected "top readmitters" views, with a documented footnote.
- Reporting both aggregate and encounter-class-specific metrics.

> [!WARNING]
> Removing legitimate high-utilisation patients simply because they are extreme can introduce bias into healthcare utilisation analysis.

## Finding D: Zero Payer Coverage Does Not Always Mean Uninsured

### Observation

Among encounters where:

```sql
PAYER_COVERAGE = 0
```

there are **13,586 encounters** in total.

However:

- **8,807** are associated with `NO_INSURANCE`
- **4,779** are associated with named insurers

The latter group includes insurers such as:

```text
Humana
Aetna
UnitedHealthcare
Cigna
Anthem
```

### Interpretation

A patient can be insured while their insurer contributes **$0 to a specific encounter**.

Potential real-world explanations include:

- High deductibles not yet met
- Claim denials
- Services not covered by the policy
- Cost-sharing arrangements
- Other payer-specific conditions

Therefore:

```text
Zero Coverage ≠ Uninsured
```

### Decision

Two separate metrics are retained and reported:

| Metric | Definition | Encounters |
|---|---|---:|
| **Zero Payer Coverage** | `PAYER_COVERAGE = 0` | 13,586 |
| **Uninsured Encounters** | `PAYER = 'NO_INSURANCE'` | 8,807 |

> [!IMPORTANT]
> These metrics answer different questions and should **not be used interchangeably**.

Reporting only one without defining it could lead to incorrect conclusions about insurance coverage.

# 🧭 Analytical Interpretation Decisions

Several requirements in the original analytics brief allowed multiple technically valid interpretations.

Rather than silently selecting one definition, each interpretation was explicitly documented and implemented consistently.

| Business Question | Interpretation Used | Alternative Interpretation |
|---|---|---|
| **"Zero payer coverage" (2a)** | `PAYER_COVERAGE = 0` | `PAYER = 'NO_INSURANCE'` |
| **"Admitted each quarter" (3a)** | Any encounter | `ENCOUNTERCLASS = 'inpatient'` |
| **"Readmitted within 30 days" (3b)** | Any encounter within 30 days of a prior encounter | Inpatient-to-inpatient only |

---

## Readmission Definition: Broad vs. Strict

For the **30-day readmission analysis**, two definitions were evaluated.

### Broad Definition

A patient is counted when **any encounter occurs within 30 days of a previous encounter**.

**Result:** **772 patients (~79%)**

### Strict Definition

Only **inpatient-to-inpatient readmissions** occurring within 30 days are counted.

**Result:** Approximately **29 patients**

### Decision

Both calculations were preserved because they answer different analytical questions.

```text
Broad Definition
Any Encounter ────────> Any Encounter within 30 days
         │
         └── Measures repeat healthcare utilisation


Strict Definition
Inpatient ────────────> Inpatient within 30 days
         │
         └── Measures a more traditional readmission concept
```

> [!NOTE]
> Alternative query implementations are preserved as commented variants in the SQL scripts where relevant.

# 💡 Key Lessons Learned

### 1. Always Validate Missing Values After Data Ingestion

> **Empty strings and `NULL` are not the same thing.**

A successful `BULK INSERT` does not guarantee semantic correctness. Missing-value representation should always be validated before analysis begins.

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(column_name) AS non_null_values
FROM table_name;
```

---

### 2. Row Counts Alone Are Not Enough

A table can have an apparently correct row count while still containing relationship-level problems.

A simple `LEFT JOIN` is an effective way to identify broken foreign-key relationships:

```sql
SELECT e.*
FROM encounters e
LEFT JOIN patients p
    ON e.patient_id = p.id
WHERE p.id IS NULL;
```

> **Data validation should test relationships, not just individual tables.**

---

### 3. Treat Data Cleaning as a Documented Decision Process

Terms such as:

- "Zero coverage"
- "Admission"
- "Readmission"
- "Active patient"

can have multiple valid definitions.

The analytical workflow should therefore document:

1. **What the data literally contains**
2. **How the business question is interpreted**
3. **Which definition is implemented**
4. **What alternative definitions exist**

> [!TIP]
> **This distinction separates data analysis from simply writing queries.**
